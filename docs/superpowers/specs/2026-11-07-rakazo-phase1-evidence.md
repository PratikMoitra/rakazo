# Phase 1 evidence

Sanitized record for review. No connection strings, passwords, or production hosts. This is not a release. Alaric must re-review the new head. Phase 1 remains incomplete.

## Units

`MAX_UPLOAD_SIZE_MB` is a count of mebibytes, 1 through 25. The byte ceiling is 26214400. The environment parser rejects `26`, `26214400`, `0`, `-1`, and `1.5`. A stored policy is a byte count in steps of 1048576, at most 26214400. A stored value cannot raise an explicit environment ceiling. An invalid stored value fails closed to 1 byte with source `invalid`. The database check rejects any other non-null value.

The signed-in RPC body ceiling for a 26214400-byte file is 36001112 bytes. The limiter keeps that body, and the JSON parser and base64 decoder keep further copies. That is not a 25 MiB memory cap.

## Request shape

`phase1-foundation.postgres.test.ts` calls Hono `app.request`. Those are in-process application requests, not a listening socket.

`phase1-wire.postgres.test.ts` listens on `127.0.0.1` port 0. Node parses the chunked bytes. The app is called with that decoded body. A partial body is acknowledged before the socket is destroyed, and a bad chunk is rejected by the parser before the app is called.

## Tested

- In-process uploads of 26214399 and 26214400 bytes accepted, and 26214401 rejected with `upload_too_large`, on disposable Postgres.
- In-process chunked small upload accepted. Unfinished body returned `upload_incomplete`. A short Content-Length with a body over the ceiling returned 413.
- Listening-socket chunked uploads of 26214399 and 26214400 bytes accepted, and 26214401 rejected with `upload_too_large` and no artifact of that name. The server recorded a nonempty partial JSON body containing `contentBase64` before the client destroyed the socket. That request added no artifact. A chunk size of `ZZ` produced `HPE_INVALID_CHUNK_SIZE`, an HTTP 400, and no call into the upload route.
- Two organization owners were denied `uploadPolicy/set` on the route. The direct service call covered one of those owners and the unverified configured admin. The verified admin was then allowed. The change wrote one `upload.policy.changed` event with previous bytes, new bytes, and a sequence number. That sequence is the highest retained row plus one, not a lifetime counter. Repeating the same value did not write another.
- Two concurrent requests for different byte counts produced ordered events. Two later requests for the same new value, starting from a different stored value, produced one transition. The sequence chain links each previous value to the prior new value without using `createdAt`. A trigger that rejects that audit insert returned a server error and left the stored value and event count unchanged. The trigger is dropped in `finally`.
- An explicit environment ceiling locked the stored value for the verified admin.

- Supervisor HTTP, still in-process, accepted a 26214400-byte file body past the size gate and rejected 26214401 with `upload_too_large` before starting a computer. A caller `maxFileBytes` of 1 did not shrink the process ceiling, and a caller `maxFileBytes` of 99999999 did not raise it. No Docker daemon was available.
- Scripted chat completed. Shutdown requeue returned the run to queued. A stale fence did not.
- Runtime role `rakazo_phase1_runtime` is not a superuser and does not have BYPASSRLS. `describeRowSecurity` reported enforced. `artifacts` and `messages` have row security on. Another space could not read the artifact through the API or through a tenant query.
- A login that is not the runtime role, with usage on `graphile_worker` and no table grants, was denied select, update, delete, and insert on `graphile_worker._private_jobs`. The runtime role could still select that table.
- Local email emulator captured the welcome message. No paid model call.
- Mobile source tests covered the advertised byte limit, a loopback default, a private custom server, and sign-in plus `me` against that server.
- On a fresh disposable database, the ordered migration chain applied. Null, 1048576, and 26214400 were accepted. 0, 1, -1, a non-mebibyte, and a value above 26214400 were rejected by the check. A pre-existing invalid row made the check statement fail and stayed unchanged.

## Queue boundary, credential cleanup only

The permanent no-reuse key is `sha256` of the domain string `rakazo-credential-object-v1:` plus the object reference. The raw reference stays on a non-terminal `credential_retirement` row and, for an uncommitted object, on `credential_orphan` with `retain_until` one hour ahead. Nothing in the production installer deletes those orphan rows. There is no alert, backlog age, or cleanup SLA. Real orphan accumulation is not accepted. Rotation and disconnect still throw before creating work when the worker URL is unset.

Attach, capture, enqueue, and the installation trigger take `pg_advisory_xact_lock` on that fingerprint and then lock the fingerprint row, through commit. On a cluster created for the test, the same installation id was inserted while its fingerprint was active. A second connection's `INSERT` of that same id waited during the original capture, delete, and enqueue transaction. That waiting statement failed with SQLSTATE 23514 and did not insert a row. After the redacted retirement row was purged, registering the same key still failed with SQLSTATE 23514 and the fingerprint stayed retired. The API login cannot disable that trigger, set `session_replication_role` to `replica`, `SET ROLE` to the queue owner, or update the fingerprint table (SQLSTATE 42501). A database owner can still bypass this. It is not DBA-proof.

Claim returns `ready`, `busy`, `terminal`, or `missing`. A busy lease, a renewal that changes 0 rows, and a missing fingerprint throw `credential_cleanup_retry` or `credential_cleanup_invariant`. They are not success. Setting `leased_until` in the past let another claim take the row; the old fence renewed 0 rows. A delete that then threw left the dummy value gone and the row leased. The following restart is operator-assisted: the test cleared the Graphile lock and set the product lease in the past. That is not autonomous recovery and it is not an exactly-once external delete.

`pnpm --filter @rakazo/api db:migrate` runs the legacy-state preflight before Prisma DDL. The queue suite does this on a PostgreSQL cluster `initdb` created for that run. It does not open the preserved database. Pending, leased, deleted, and skipped retirement rows plus one active ciphertext were left in place, and `_prisma_migrations` was not created. No converter and no delete runs to clear that guard. An existing `rakazo_credential_worker` role with no provenance row was not altered: a boolean comparison of the password verifier stayed true, and no migrations were written. The worker and API packages declare the same `pg` version the database package uses, and the parser is a direct import of `pg-connection-string` rather than a lookup from the bundled file. Those clients set TLS off explicitly and refuse an ambient TLS mode or startup-options variable. A missing password is refused instead of reading an ambient password. The worker URL is parsed with that parser before a client exists. Query overrides for host, port, user, password, host address, duplicate or encoded routing keys, sockets, and TLS weakening are rejected with no client. The client is built from the parsed host, port, database, user, and password, not by handing the original string back to the driver. The migration engine URL is rebuilt from those parsed fields and checked with the same parser before a spawn. That check is an offline identity comparison. It is not a live engine connection, and it is not a claim that every Prisma entrypoint outside the guarded spawn was executed. After bootstrap, the worker login connects as itself and the command checks `session_user`, `current_user`, database, and `system_identifier`.

The production worker rejects `PHASE1_DUMMY_SECRET_STORE` and `PHASE1_DUMMY_CRASH_AFTER_DELETE` before it opens a database or a secret store. `NODE_ENV` does not bypass that. The file dummy and the crash exit live in `apps/worker/src/phase1-cleanup-fixture-main.ts`. The production build entries are `src/index.ts` and `src/health-check.ts`. The root `.dockerignore` excludes that fixture and the phase-1 test files from the Compose, Railway, and topology build contexts. The preview image is derived from the server image and was not built here. No Docker daemon was used, so image contents were not inspected. Fixture child processes receive an allowlisted environment. `REALTIME_DATABASE_URL` is the fixture database. An ambient sentinel is not copied. The fixture cluster treats a start attempt as live even when `pg_ctl start` returns an error. It stops that data directory and continues only when status reports the documented not-running exit. An unknown status or a server that is still running keeps the directory. That fixture process deleted the retired dummy value and exited 75. The operator-assisted second start acknowledged the job. The current ciphertext remained. A committed legacy raw-reference job stayed queued, and the next start's process close status was 1, with `legacy jobs are queued` in the output. `apps/api/src/phase1-cleanup-once.ts` is not this evidence.

The runtime login still has Graphile access for every other job when migrate provisions separate URLs. That all-job gap stays open. This slice does not revoke those grants and is not a pattern for the other jobs.

The chunk-size and partial-body checks use a custom Node bridge. The production HTTP adapter was exercised with one 32-byte chunked upload. That does not cover the 26214400-byte boundary, abort, or parser rejection.
